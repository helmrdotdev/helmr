# Slack conversation fixture

This fixture supplies synthetic Agent behavior for a human-operated Slack check.
Compilation validates definitions and source bundles. It does not qualify a live
Worker, Saves, Slack consent, delivery, rendering, notifications or controls.
The fixture neither sends Slack messages automatically nor provisions infrastructure.

Prepare an isolated project with locally packed SDK bytes:

```sh
nix develop -c python3 tests/e2e/prepare_project.py /private/slack-case-project \
  --fixtures cases/slack-conversation
```

Use the explicitly selected disposable Environment, a reachable HTTPS Control
Plane and functioning Worker/Dispatcher with the exact candidate artifacts.
Record source revision, package identity and Deployment ID. Each independently
allocated Computer requests 1 vCPU and 1 GiB; handlers have ten-minute limits.
Bound concurrent starts to available capacity. App changes and deployment require
separate authorization.

## Dedicated Apps and human identity

In Console, open each Agent's Slack connection setup. Publish Alpha and Beta using
separate dedicated Apps. Publish the coordinator too when testing owned delegation.
Use the manifest generated by that exact setup: its callback paths include the
registration ID. The checked-in `app-manifest.json` is only a readable template;
its origin and `REGISTRATION_ID` are placeholders. Do not import it unchanged.
The generated manifest and installation authorization share the scopes in
`internal/slack/installation_authorization.go`; native Agent features require
`features.agent_view` and `assistant:write`.

Keep app secrets in normal secret custody and out of source, logs and evidence.
Token rotation is a one-way app setting: obtain authorization before creating or
changing a real App. Preserve existing app policy when reusing an authorized test
App. Each live registration must have its own correct event and interaction
callbacks; never point another Agent's registration at the same App. Do not copy
installation tokens between databases.

Complete installation through Console and invite each App to the designated test
channel. Slack's installed App identity supplies its name and avatar. A conversation
has one front Agent; mentioning another App inside its thread does not add a second
speaker or select a different Agent.

For a first-use check, mention Alpha from an unlinked test identity. Follow the
private connection hint, authenticate through the existing Helmr login, complete
separate Slack OpenID consent and explicitly confirm the identity link. An existing
organization member can complete this flow; otherwise an organization invitation
is required. Return to Slack and send a fresh request. The rejected request must
never replay automatically. Bot installation consent and human identity consent
remain separate. A confirmed workspace identity link works across that workspace's
Agent Apps.

## Commands and observations

Mention Alpha's installed bot followed directly by
`case:progress marker:unique_01`. Markers contain 1–64 ASCII letters, digits,
underscores or hyphens. Ordinary replies continue the front Agent's conversation.
For Console/API admission, initial input is a text-part array:

```json
[{"type":"text","text":"case:progress marker:unique_01"}]
```

An explicit Slack destination uses the actual Slack channel ID, for example
`slack: { channelId: "C0123456789" }` in the SDK. API and cron starts create an
explicit opening even when the Agent later emits no authored content. Inspect
those openings separately from a human-authored Slack root.

| Mode | Stimulus and required observation |
| --- | --- |
| `progress` | Three ordered text/JSON outputs followed by a staged response. Compare Slack with retained events and the Turn's completed/own-Save boundary. |
| `long` | Twenty-four outputs with about 1.8 KiB of text plus JSON each. Inspect continuation, order and absence of duplicate or missing content. Announce this verbose test first. |
| `text` | Text question and twelve progress outputs over about eighteen seconds. Answer during progress and inspect authenticated attribution and the retained answer. |
| `choice` | Two structured choices plus optional text, alongside progress. Compare the retained canonical answer, including JSON null. |
| `withdraw` | Leave the question unanswered. After fifteen seconds the Agent cancels it. Observe removal of answer controls while progress continues. Answering intentionally fails the case. |
| `empty` | Stage an empty response. Observe successful settlement without an invented response body. |
| `silent` | Return only a private result. Observe settlement without leaking that result. |
| `multi` | Start Alpha with a marker of at most 59 characters. Its runtime `start` operation starts an independent Beta choice conversation on the same Computer. Answer each conversation independently. |
| `stop` | Emit a waiting message, then wait for up to eight minutes. Stop the conversation through Console and inspect interruption, hold and physical stop. Failure to stop fails this case. |

Every completed case returns `PRIVATE_RETURN_<marker>` privately. This value must
remain absent from Slack and output/response events. Answers remain absent from
thread posts; retained ask records, `ask.responded` events and authorized Console
reads contain the answer. Post-answer fixture output contains only marker,
speaker, phase and responder kind.

For `multi`, both Apps must be published in the same workspace and able to access
the channel. Beta opens a new root sent through Alpha's App, with a structured
Beta mention and source permalink. Beta's subsequent output uses Beta's App.
Inspect both Session IDs and roots. Beta's completion must not clear Alpha's
question. Independent `start` does not create an owned child or share the parent's
conversation. Use an existing compatible Computer for API starts if retained
reservations fill the test Environment.

For owned delegation, start `verification-coordinator` with
`case:progress marker:<unique marker>` and a marker of at most 58 characters.
The coordinator uses runtime `spawn` to create Beta on its Computer and waits for
that exact Turn. Beta's authored content appears in the coordinator's existing
conversation with delegated-work context and its Turn activity card. There is no
second conversation root, and the sending identity remains the coordinator App.
Inspect complete text/JSON content, stable task identity, private-result isolation
and coordinator completion. This child does not ask questions: human questions
belong to the front Agent. The activity surface's **Stop conversation** control
targets the front and its owned work; inspect stopping until physical cessation.

## Native acceptance and cleanup

Verify native ongoing status, ordered authored progress, question prominence,
answer controls disappearing after answer/withdrawal, and absence of invented
completion prose. A staged response becomes visible only after successful
settlement. Inspect late steering rejection or uncertain delivery against the
retained receipt; no automatic resend is permitted.

Record desktop/mobile rendering, control behavior and notification attribution
separately. Qualify public/private channels and shared-channel rejection only in
designated channels with the required audience. One user's private-channel view
cannot establish another user's visibility or mobile notification behavior.

The fixture does not inject authority loss, duplicate receipts, uncertain delivery
or token refresh. Those require separately specified authorized operations and
sanitized observations. Reauthorization does not prove refresh. Local injected
faults do not prove live Slack behavior. Fast completion may not expose saving;
claim saving-time controls only after observing that phase in a controlled native
operation.

Track exact Session, Turn, Computer and Slack thread IDs for every marker,
including failed cases. Cancel owned open Sessions, reclaim their Computers through
normal APIs and confirm physical/storage cleanup. Restore only settings changed
by this campaign and disconnect its test publications when authorized. Disconnect
neither promises remote token revocation nor erases Slack history. Retain the App
and managed credentials unless its owner authorizes retirement. Remove only owned
messages when cleanup is authorized. Preserve sanitized evidence before retrying.
